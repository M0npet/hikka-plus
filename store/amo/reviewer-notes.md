Notes to reviewer — Hikka Plus

WHAT IT DOES
Unofficial extension for hikka.io (Ukrainian anime/manga tracker). On hikka.io title pages it adds, inside its own Shadow DOM hosts (<hikka-plus-*>), a "Watch" block with embedded third-party players for anime and a "Chapters" block plus an overlay reader for manga/light novels from Ukrainian source sites. No server of our own, no analytics, no remote code. Interface is Ukrainian.

HOW TO TEST
1. Open any anime page from https://hikka.io/anime (a popular, already aired title) — the "Перегляд" (Watch) block appears below the description; pick an episode.
2. Open any manga page from https://hikka.io/manga — the "Розділи" (Chapters) block; click a chapter — the reader opens over the page. Light novels: https://hikka.io/novel.
3. Toolbar icon — settings window (tabs: Sources / Hikka / Reader / Player / Data).
Signing in to Hikka is optional (OAuth on hikka.io; any free Hikka account works). Without it everything except updating the Hikka list works.

SOURCE CODE / BUILD
Source archive is attached (same as the public repo https://github.com/M0npet/hikka-plus at this version's tag).
Requirements: Node.js 22, npm 10 (Ubuntu 24.04 or Windows 11).
  npm ci
  npm run build-for-amo        (= wxt build -b firefox; output: .output/firefox-mv2)
Built with WXT 0.21 (Vite/Rollup); React components are compiled against Preact (preact/compat alias in wxt.config.ts). All third-party code comes from npm via package-lock.json; no library is modified.
The Hikka OAuth client reference/secret are injected at build time from env WXT_HIKKA_CLIENT_REFERENCE / WXT_HIKKA_CLIENT_SECRET. Without them the build is identical except these two strings in background.js; the values are visible in the submitted background.js — set them as env vars for a byte-identical build. It is the OAuth client of a browser extension, so it is public by nature (anyone can read it from the package).

PERMISSIONS
- storage — settings, reading/watching progress, Hikka token (local only); sync storage for progress across the user's devices.
- alarms — background check for new episodes in the user's dub team every 3 h (src/watch/dub-check.ts): for ≤40 anime the user watched in our player, GET api.mikai.me/public/v1/anime/hikka:<slug>/player (same public API and request as the player; credentials: 'omit'; 1.5 s between requests; stops on 429), then a count on the toolbar icon. Toggle in the "Player" tab.
- OPTIONAL notifications — only if the user enables "Browser notifications" for new dub episodes (permissions.request on that click; removed when turned off). Clicking a notification opens the title on hikka.io.
- https://hikka.io/* — content script that adds our blocks to title pages.
- https://api.hikka.io/* — title data (names, external links, MAL id); with the user's OAuth consent: read/update the user's read/watch list entry for the opened title. Plus the public episode schedule (POST /schedule/anime, no auth) every 3 h for card badges, and the public episode titles of the opened anime (GET /anime/<slug>/episodes, no auth, cached locally for 3 days), and its franchise relations to find the next season (GET /related/anime/<slug>/franchise, no auth, cached locally for 3 days); on the last episode with no next season, the user's public "Watching" list (POST /watch/<username>/list, no auth; the username comes from the Hikka page's own query cache via entrypoints/hikka-bridge.ts, stored locally; can be turned off).
- Manga/novel sources (api.zenko.online, manga.in.ua, baka.in.ua, data/search.api.honey-manga.com.ua, uamanga.com, back.animesvit.com, dgmanga.app, runi.ink, api.smakolykytl.site, novel.org.ua, fan-vers.com, www.wattpad.com) — search by title name, chapter list, chapter pages/text. Requests go from the background script (CORS) with credentials: 'omit', only to an allowlist (src/core/hosts.ts, isAllowedUrl).
- Link-only sources (mangra.app, faust-web.com, mangarama.com.ua, manga.valsky.org) — public search to build a "read on <site>" link; nothing is read from them.
- www.animefillerlist.com (redirects to animefillerlist.com) — episode types (filler / mixed / anime canon) for the episode grid, anime with 24+ episodes only: GET /shows (show list, cached 14 days) and GET /shows/<slug> of the title matched by exact English/romaji name (cached 7 days), parsed with DOMParser in the content script (src/watch/fillers.ts); no user data. Toggle in the "Player" tab.
- api.mikai.me, animeon.club — list of dubs/episodes and player iframe URLs for the opened anime. Plus, as a fallback for episode types, GET api.mikai.me/public/v1/anime/hikka:<slug>?include=uaPosters → episodeTypes.
- api.aniskip.com — MAL id + episode number to find where the ending starts (the episode counts as watched from there).
- Content script in player iframes (ashdi.vip/vod/*, moonanime.art|net/iframe/*, fenixplay.xyz/*) — entrypoints/player-frame.content.ts. Runs only in our own iframe (window.name === 'hikka-plus') and only on request from https://hikka.io: draws the video into a 32×18 canvas five times per second (only while our player is on screen, unless the experimental device lighting is on) and posts the colours to hikka.io for the ambient glow around the player. The only thing it changes is video.currentTime — and only when the user clicks "Skip opening/ending" or the marks bar (or turned on auto-skip); opening/ending marks come from the player itself or AniSkip. It also resets a playback speed above 4× (left in the player's localStorage by the 0.5.22 marks scanner, now removed) back to 1×. It does not touch the player UI and does not extract streams. Cross-origin video without CORS → it reports "off" and stops.
- web_accessible_resources hikka-bridge.js (hikka.io only) — tiny script injected into the page context: after we update the Hikka list it invalidates the page's own React Query cache so Hikka's widget shows the new number; it also listens to that cache to read the current counter and, for signed-in Hikka users, their title-language preference (`profileUi`, GET /user/me/ui — already loaded by Hikka itself; stored locally so our names use the same language). It does not modify Hikka's DOM.
- "Lights off" adds our own <hikka-plus-dim> element (Shadow DOM) to body with four dark rectangles around the player; removed on click/Esc.
- OPTIONAL http://*/* and https://*/* (+ optional data collection "websiteContent") — experimental "device lighting" (off by default; Player tab). The address of the user's TV (Philips JointSpace), WLED controller or Hue bridge in the home network is typed by the user, so it is not known in advance. On "Connect" we call permissions.request for that one origin only (plus websiteContent consent), never for all URLs; Razer Chroma asks for http://localhost/* and https://chromasdk.io/* (Chroma REST SDK on ports 54235/54236). Only edge colours of the frame are sent, only to those user-entered local devices (src/lights/).

DATA COLLECTION (manifest data_collection_permissions)
required: browsingActivity (slug/names of the opened title go to Hikka API, sources, Mikai, AnimeON, AniSkip).
optional (since 0.6.1): authenticationInfo (Hikka OAuth token, stored locally, sent only to api.hikka.io) + websiteActivity (read chapters / watched episodes written to the user's Hikka list) — requested together via permissions.request({data_collection}) when the user clicks "Увійти" (Sign in) in the extension's settings page (src/settings/app.tsx → requestHikkaData in src/core/hikka-auth.ts). The sign-in buttons on hikka.io pages cannot call the permissions API, so they ask the background, which opens the settings page on the Hikka tab if consent is missing. Without consent the background refuses the token exchange and every Hikka list request, and it drops a stored token when the consent is revoked (permissions.onRemoved) or missing at startup (src/core/hikka-api.ts, entrypoints/background.ts).
optional: websiteContent (frame colours to the user's own lighting devices).
Card badges "▶ N new chapters" (manga/novel, since 0.6.1): at most every 3 h per title, for "Reading" titles visible on the current Hikka page and already linked to a source, the content script reloads the chapter list from that same source (same request as opening the title; no new hosts). Read counts come from Hikka's own page cache (no API calls) — src/cards/released.ts.

Ukrainian posters (anime/manga/novel, on by default, toggle in the "Hikka" tab). Anime: slugs of anime cards visible on the Hikka page go to Mikai's public API in one batch request (GET api.mikai.me/public/v1/anime/batch?source=hikka&ids=…, ≤100 ids, ≤1 request / 2 s, each slug cached 3–14 days; Mikai allowed us to use the API), and `images.uaPoster` is shown if present. Manga/novel: for titles already linked to Zenko / Honey Manga / DGManga / Manga.in.ua (novels: Baka / Honey Manga / DGManga), the extension calls the source's getTitle once when the title is opened (then at most every 14 days, same hosts as the reader) and stores the cover URL in `local:hp:covers`. On Hikka pages the content script inserts its own `<hikka-plus-cover>` element (own Shadow DOM, plain `<img referrerpolicy="no-referrer">`, pointer-events: none) over the poster; Hikka's DOM is not modified otherwise — src/cards/covers.ts, src/cards/cards.ts.
Full policy: PRIVACY.md (Ukrainian + English) in the source archive and repo.

LINTER WARNINGS
UNSAFE_VAR_ASSIGNMENT (innerHTML) come from preact/compat rendering dangerouslySetInnerHTML (chunks/mount*, content.js). Our only use is light-novel chapter text in src/features/reader/views.tsx, which is sanitized with DOMPurify right before rendering.

Third-party players (Ashdi, Moon, Fenix) are embedded as plain iframes exactly as on the source sites; their pages are not controlled by the extension and may contain their own ads.
